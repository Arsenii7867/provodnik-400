# Проводник 400

Тренажёр нештатных ситуаций для проводников ВСМ-400: сотрудник проходит ветвящиеся сценарии по
карточкам «Ситуаций на борту» и стандартам СТО РЖД, принимает решения под серверным таймером и
видит, как каждое решение двигает две шкалы, лояльность пассажира и рейтинг безопасности.
После прохождения разбор объясняет каждый ход со ссылкой на норму, очки идут в профиль,
достижения, лидерборд бригады и аналитику компетенций; HR и LMS забирают результаты через API.
Сценарии лежат в YAML и меняются без пересборки.

## Как запустить

### Windows: одна кнопка

Нужен только Docker Desktop. Дважды щёлкните `start.cmd` в корне проекта. Скрипт:

1. сохранит существующий `.env` или один раз создаст его из `.env.example`;
2. при необходимости попросит Docker Desktop запустить движок;
3. соберёт frontend и backend, поднимет контейнер и заполнит пустую демо-базу;
4. дождётся готовности базы, сценариев и интерфейса, затем откроет браузер.

Первый запуск дольше последующих, потому что Docker скачивает базовые образы. Приложение
откроется на `http://localhost:8000`. Для остановки дважды щёлкните `stop.cmd`: база останется
в именованном Docker-томе и будет доступна при следующем запуске.

Если порт 8000 занят, добавьте в `.env` строку `APP_PORT=8011` и снова запустите `start.cmd`.
Тот же сценарий из PowerShell без автоматического открытия браузера:

```powershell
.\scripts\start.ps1 -NoBrowser
```

Linux и macOS:

```bash
./scripts/start.sh
./scripts/stop.sh
```

Статус контейнера: `docker compose ps`, журнал: `docker compose logs --tail=100 app`.
`GET /api/health` проверяет живость процесса, а `GET /api/health/ready` возвращает 200 только
когда доступны база, валидный контент и собранный интерфейс. Swagger доступен на
`http://localhost:8000/docs`.

Демо-вход: коды `VSM-1001` и `VSM-1002` (проводники), `VSM-2001` (наставник), PIN `1234`.
Все сотрудники синтетические. Сид идемпотентен и заполняет только пустую базу.

### Запуск без Docker для разработки

Нужны Python 3.13 и Node 24 LTS. Команды выполняются из корня репозитория. Сначала соберите
frontend, который сервер раздаёт с того же порта:

```
cd frontend
npm ci
npm run build
cd ..
```

Скопируйте `.env.example` в `.env`, не перезаписывая существующий файл. Затем запустите сервер;
`--env-file ../.env` явно загружает настройки, а `AUTO_SEED=1` заполняет пустую базу.

Windows (PowerShell):

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
cd backend
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --env-file ../.env --host 127.0.0.1 --port 8000 --no-proxy-headers
```

Linux и macOS:

```bash
[ -f .env ] || cp .env.example .env
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --env-file ../.env --host 127.0.0.1 --port 8000 --no-proxy-headers
```

Сервер занимает терминал; для дальнейших команд откройте второй. Ручная команда
`python -m app.seed` читает только переменные окружения процесса, `.env` сама не загружает;
для обычного запуска она не нужна. Флаг `--no-proxy-headers` запрещает uvicorn доверять
`X-Forwarded-For`: за доверенным обратным прокси флаг убирают. Полный список настроек и
пояснения находятся в `.env.example`.

Для разработки фронта `npm run dev` поднимает Vite на `http://localhost:5173` с прокси
запросов `/api` на сервер.

## Проверка

Тесты и линтер живут в отдельном файле зависимостей, из папки `backend`:

```
pip install -r requirements-dev.txt
python -m pytest -q
python -m ruff check .
python -m app.scenarios.validator ../content
```

Из папки `frontend`: `npm test` (логика таймера и графиков). Перед первой сквозной проверкой
установите браузер: `npx playwright install chromium` (на Linux зависимости системы ставит
`npx playwright install --with-deps chromium`). Затем `npm run build` и `npx playwright test`:
проверки сами поднимают сервер на порту 8010 с собранным фронтом. Все проверки разом запускает
`bash scripts/check.sh` из корня репозитория после установки зависимостей сервера, фронта и
браузера. На Windows для скрипта нужен Git Bash.

## Где что лежит

| Путь | Что там |
|---|---|
| `backend/app` | сервер на FastAPI: настройки, база, вход по коду и PIN, единый формат ошибок |
| `backend/app/api` | маршруты по доменам: авторизация, профиль, сценарии, прохождение, разбор, достижения, лидерборд, уведомления, челленджи, аналитика, интеграция, администрирование |
| `backend/app/scenarios` | движок прохождения, загрузчик, валидатор, перебор путей, граф и хранилище контента с перечитыванием |
| `backend/app/services` | прохождение с серверными таймерами, итог, XP и уровни, достижения, челленджи, уведомления, события для LMS, рейтинг, аналитика |
| `backend/tests` | тесты pytest на временной SQLite, сломанные сценарии в `tests/fixtures/broken` |
| `content` | справочники и сценарии в YAML, формат в `docs/scenarios.md` |
| `frontend/src` | интерфейс на React, данные только через `src/lib/api.js` |
| `frontend/e2e` | сквозные проверки Playwright |
| `docs` | архитектура с диаграммами, API, пользовательские сценарии, формат сценариев, безопасность, план развития, `openapi.json` |
| `Dockerfile`, `compose.yaml` | воспроизводимая сборка и изолированный локальный запуск с постоянной базой |
| `start.cmd`, `stop.cmd`, `scripts/start.*` | запуск, ожидание готовности, открытие браузера и безопасная остановка |
| `scripts/check.sh` | все проверки одной командой |

## Как добавить сценарий

1. Создать `content/scenarios/<id>.yaml` по образцу `content/scenarios/smoking_vestibule.yaml`:
   шапка, контекст, стартовые шкалы, узлы с вариантами, таймер с веткой истечения, разбор с
   ссылками на `content/refs.yaml`.
2. Запустить валидатор из папки `backend`: `python -m app.scenarios.validator ../content`,
   добиться строки `ИТОГ` с `ошибок=0`.
3. Ничего не перезапускать: сервер перечитывает изменённые файлы сам, наставник может нажать
   `POST /api/admin/scenarios/reload`, и все сотрудники получат уведомление о новом сценарии.
   Подробности и репетиции живого изменения в `docs/scenarios.md`.

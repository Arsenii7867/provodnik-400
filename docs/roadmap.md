# Ограничения и план развития

Исправления из [ревью от 27 сентября](audit-2026-09-27.md) ограничили ожидание сети, добавили
чтение неподтверждённых событий LMS и сохранение фактического лимита таймера. Затем были
изолированы [состояния прохождений](play-route-isolation.md), защищены
[замеры серверного времени](clock-samples.md), добавлен [ручной повтор загрузки](load-retry.md).
Новые прохождения сохраняют [исторический разбор](historical-debrief.md). Результаты для
проверенных ревизий приведены в [сводке CI](verification.md).

## Что есть сейчас

Тренажёр работает в одном процессе. В нём восемь ветвящихся сценариев по карточкам «Ситуаций
на борту» и стандартам СТО РЖД, серверные таймеры, две шкалы и разбор с цитатами норм.
Результаты доступны в профиле, достижениях, лидерборде и личной или бригадной аналитике.
Есть челленджи со сгорающими баллами, уведомления, API для HR и LMS. YAML-контент проверяется
валидатором и меняется без пересборки.

## Ограничения

1. Контент: восемь сценариев по набору из 51 исходной карточки ситуаций. По исходному классу
   сценария: «комфорт» 3, «первый» 1, «стандарт» 2, «бизнес» 2. Методист пишет сценарии в YAML
   и проверяет их валидатором в терминале. Редактора в интерфейсе нет.
2. База: в демо SQLite файлом (`backend/data`), один процесс uvicorn. Совместимость PostgreSQL 17,
   браузеры и ограниченную нагрузку проверяет [отдельный workflow](extended-checks.md).
   Горизонтальное масштабирование и длительная нагрузка в этот набор не входят.
3. Развёртывание: локальный Docker/Compose и запуск одной кнопкой готовы, но сервер для
   онлайн-демо и production-профиль с PostgreSQL, TLS, миграциями и резервным копированием не
   подняты.
4. Лимит попыток входа хранится в памяти процесса. При перезапуске счётчики теряются,
   при нескольких воркерах считаются раздельно.
5. Люди и история синтетические: имена из словарей, прохождения сгенерированы движком с
   заданным зерном. Контракт интеграционного API проверен тестами и сквозными запросами;
   реальная внешняя HR-система или LMS не подключена.
6. Офлайн-режима нет: прохождение требует соединения с сервером на каждом ходу, потому что
   таймер и исход решает сервер.
7. Аналитика рассчитывается при каждом чтении истории сотрудника, без кэша. Недели
   определяются по датам UTC. Уведомления ограничены последними ста, пагинации нет.
8. Новые разборы сохраняют объяснения и нормы каждого хода и полный итог в JSON состояния.
   Старые завершённые записи без снимка используют доступный текущий контент (`legacy`);
   старые активные попытки могут завершиться с неполной историей пояснений (`partial`).
   Утраченные тексты нельзя восстановить достоверно. Формат и границы описаны в
   [решении об историческом разборе](historical-debrief.md).
9. Исходящие события для LMS лежат в таблице: архив читается по курсору, непрерывная доставка
   через `pending_only=true` возвращает неподтверждённые события до ACK. Подтверждения общие
   для одного логического потребителя; доставки по webhook и раздельных ACK для HR/LMS нет.
10. У сотрудника одно активное прохождение: старт нового прерывает незаконченное.

## План развития

1. Расширить контент до 51 ситуации. Спроектированы следующие четыре сценария: конфликт
   из-за детей в комфорт-классе, розетка и планшет в первом классе, животное без переноски
   и сосед с аллергией, задержка в пути и жалоба. Затем добавить остальные карточки по
   классам обслуживания, покрыв каждую компетенцию не меньше чем тремя сценариями.
2. Разметка компетенций методистами: веса компетенций по сценариям, привязка каждой нормы к
   пунктам стандартов с проверкой реконструированной нумерации, редактирование `content/refs.yaml` из
   интерфейса.
3. Редактор сценариев в интерфейсе наставника: форма узла и варианта, встроенный валидатор с
   теми же кодами ошибок, предпросмотр графа и путей, публикация через существующий
   `POST /api/admin/scenarios/reload`.
4. Подготовить промышленное развёртывание: профиль Compose/Helm с PostgreSQL,
   Alembic-миграции существующих данных, резервное копирование, установку на сервер и HTTPS
   на прокси. Локальный Docker/Compose уже есть. Совместимость с PostgreSQL проверяется
   отдельно; несколько экземпляров и production-инфраструктура пока не испытаны.
5. SSO по корпоративной учётной записи вместо PIN, httpOnly cookie с защитой от CSRF, таблица
   аудита входов, общее хранилище счётчиков лимита для нескольких процессов.
6. Мобильный клиент с офлайн-очередью для сценариев без таймера: ходы копятся на устройстве и
   применяются сервером при появлении сети, сценарии с таймером остаются только онлайн.
7. Антифрод рейтинга: сигналы аномальных прохождений (одинаковые последовательности ходов у
   разных сотрудников, серии повторов одного сценария, ответы за доли секунды), экран
   для наставника и исключение помеченных прохождений из лидерборда.
8. Бригадные челленджи: общая цель на бригаду (например, все проводники без инцидента за
   неделю), командный бонус и лидерборд бригад между депо.
9. Доставка событий в LMS по webhook с повторами и подписью, экспорт результатов в формате xAPI.
10. Кэш аналитики по последнему прохождению сотрудника, пагинация уведомлений, недели по часовому
    поясу депо. Снимки нового разбора уже предусмотрены форматом версии 1 в `state_json`;
    следующие версии должны читать прежние форматы, не выдавая восстановленные тексты за исторические.

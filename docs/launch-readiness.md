# Готовность к запуску

Состояние на 27.09.2026: локальный запуск подготовлен, задачи перед промышленной
эксплуатацией перечислены ниже. Проверка опирается на требования кейса и код репозитория.

## Локальная демонстрация

| Область | Состояние | Как проверяется |
|---|---|---|
| Запуск на Windows | `start.cmd` собирает и запускает приложение, ждёт readiness и открывает браузер | Двойной клик или `scripts/start.ps1 -NoBrowser` |
| Linux и macOS | Запуск через `scripts/start.sh` | `./scripts/start.sh --no-browser` |
| Окружение | Многоэтапная сборка Docker: Node 24 для frontend, Python 3.13 для сервера | `docker compose build` |
| Конфигурация | `.env` создаётся только при отсутствии; существующий файл не перезаписывается | Повторный запуск |
| Демо-данные | Только синтетические сотрудники; пустая база заполняется идемпотентно | Вход `VSM-1001 / 1234` |
| Хранение | SQLite вынесена в именованный том `provodnik-data` | `stop.cmd` не удаляет том |
| Живость | Лёгкий `HEAD/GET /api/health` | Мониторинг процесса |
| Готовность | База отвечает, сценарии валидны, frontend подключён; index и указанные в нём локальные скрипты и стили есть на диске | `GET /api/health/ready` |
| Защита контейнера | Непривилегированный пользователь, корневая файловая система только для чтения, capabilities удалены, порт на loopback | `docker compose config` |
| Проверка сборки | CI собирает контейнер, ждёт readiness, открывает `/` и выполняет демо-вход | Задание `container-smoke` |
| Документация | README, архитектура, OpenAPI, User Flow, сценарии, безопасность и roadmap | Папка `docs/` |

Compose публикует порт только на `127.0.0.1`. Этот профиль предназначен для локального запуска.

## Чек-лист перед демонстрацией

1. Установить Docker Desktop и убедиться, что на диске есть место для базовых образов.
2. Запустить `start.cmd` и дождаться автоматического открытия `http://localhost:8000`.
3. Проверить, что `/api/health/ready` вернул `status=ready` и все три проверки равны `true`.
4. Войти как `VSM-1001`, PIN `1234`, пройти путь из раздела «Сценарий демонстрации по кликам»
   в `user_flow.md`.
5. Открыть `/docs`, профиль, лидерборд и аналитику; проверить ветку истечения таймера.
6. После демонстрации выполнить `stop.cmd`. Данные сохранятся для повторного запуска.

Если readiness не наступил, выполните `docker compose ps`, затем
`docker compose logs --tail=100 app`. Ошибка сборки выводится в терминал. Сообщение об успешном
запуске появляется только после положительного ответа readiness.

## Задачи перед промышленным запуском

| Приоритет | Пробел | Почему это важно | Следующий шаг |
|---|---|---|---|
| P0 | Миграции схемы отсутствуют: используется `create_all` | Обновление существующей базы не меняет старые таблицы безопасно | Ввести Alembic и прогон `upgrade head` до старта |
| P0 | Нет профиля развёртывания с TLS | Uvicorn отдаёт HTTP; доверенный прокси должен обеспечивать TLS и HSTS | Добавить production Compose/Helm и nginx/корпоративный ingress |
| P0 | Нет подтверждённого backup/restore | Потеря тома означает потерю прогресса | Описать RPO/RTO, автоматический backup и учебное восстановление |
| P0 | Целевая инфраструктура PostgreSQL не испытана | API, конкурирующие транзакции, E2E и ограниченная нагрузка прошли на PostgreSQL 17 в CI, но это не проверка промышленного контура | Испытать миграции, восстановление и несколько процессов в целевом окружении |
| P1 | Сидирование состоит из двух транзакций | Прерывание между ними может оставить неполную демо-базу | Сделать сид атомарным или версионированным и возобновляемым |
| P1 | Лимит попыток входа хранится в памяти процесса | Несколько реплик считают попытки независимо | Вынести счётчик в Redis/шлюз |
| P1 | Токен лежит в `localStorage`, вход по четырёхзначному PIN | Для реальных сотрудников этого недостаточно | Корпоративный SSO, httpOnly cookie, CSRF-защита и жизненный цикл учётной записи |
| P1 | Нет метрик, трассировки и централизованного журнала | Нельзя задать и контролировать SLO | Добавить request ID, структурные логи, метрики и алерты |
| P1 | Нет согласованного SLA и длительного нагрузочного теста | Прогоны на 10/25 пользователей для SQLite и PostgreSQL ограничены одним процессом; промышленная ёмкость не установлена | Зафиксировать SLA, испытать целевую нагрузку и длительную устойчивость |
| P2 | Горизонтальное масштабирование контента не завершено | Каждый процесс держит YAML в своей памяти | Версионировать публикации сценариев и синхронно инвалидировать реплики |

До закрытия P0 готовность к промышленной эксплуатации не подтверждена.

Ревизии и результаты указаны в [сводке CI](verification.md), инструкции для PostgreSQL, E2E
и нагрузки находятся в [extended-checks.md](extended-checks.md). Скрипт Windows PowerShell
проверен чтением кода; контейнерный smoke-тест выполняется на Linux. Запуск на реальной
Windows-машине ещё нужно проверить.

## Продуктовые вопросы

- У трёх сценариев таймер начинается на первом узле сразу после создания прохождения; часть
  времени уходит на переход между экранами. Момент начала таймера остаётся открытым
  продуктовым решением в roadmap; брифинг «Я готов» - один из вариантов для согласования.
- Старт нового сценария прерывает активный после текстового предупреждения, без отдельного
  подтверждения.
- Наставник управляет контентом только через API; для регулярной работы нужен экран
  `validate -> preview -> publish` и отдельная роль автора/администратора.
- После истечения авторизации нет возврата на исходный маршрут, а неизвестный URL не имеет
  отдельного 404-экрана.

Пользовательские сценарии описаны в `user_flow.md`, защита в `security.md`, план развития
в `roadmap.md`.
